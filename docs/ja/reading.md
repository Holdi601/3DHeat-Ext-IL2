# ファイルの読み方 {#how-the-files-are-read}

| 部品 | 状態 |
|---|---|
| アーカイブ（`data/*.gtp`、Great Battles） | ファイル表（`S16R`、`STRMFAT?`、`DIR!`/`FILE` のレコード）と、そのエントリ（`STRMFILE` のヘッダー、データはそのまま保存）。テストインストールのすべての `Maps*.gtp` |
| `height.hini` | `height_map`、`water_map`、`heightMul`、`SeaLevel`、プレイ範囲、`MapNW/NE/SE/SW`。テストインストールのすべて |
| ハイトマップ（`height.dat`） | 下の符号化。作業中に完全にデコードしたマップのすべてのセクターは、そのビットストリームをちょうど使っています（余ったバイトの詰め物のみ）。残りはヘッダーで確認。ゲームが `distlod.dat` と並べて入れている非圧縮の `distlod.raw` ファイルに対して、ビット単位で一致し、マップ自身の遠景用LODのハイトマップに対して（相関 0.999）一致 |
| 高さ | メートル = 生の値 × heightMul / 256 − SeaLevel × heightMul。あるマップの海は、そのhiniのコメントが示す高さにちょうど復号されます。別のマップの境界は、その `bounds_level` にちょうど復号されます |
| 配置 | hiniの四隅の間の双線形補間。行0が北、列0が西。あるマップで、既知の町、海岸、海に対して確認しました（町の高さは実際の高さから約10m以内、海は海面下）。四隅は四角形であり、ゲーム自身の投影法ではありません。そのため、大きなマップの中央では数百メートルの誤差を見込んでください。あるマップ群のhiniは、別のマップの四隅を持っています（実際の大きさの一部しか覆いません）。これは検出され、そのマップ群は代わりに目印の位置合わせで配置されます。ゲーム自身の位置データベース（`*.ldfbin`）の町と飛行場を、実際の位置と照合します。二乗平均平方根で数キロメートル（町は、その名前の飛行場と照合。実在の場所の座標は約1キロメートル）。JSONには、すべての目印とその残差が挙がります |
| 水のマスク（`water.wtr`: 4段のピラミッド型のタイル。各タイルは400mのブロックの表。各ブロックは陸、全部水、または一部水で、その形はビットストリームにある） | コンテナはすべてのマップで読みます（完全にデコードしたファイルには余りのバイトがありません）。一部水のブロックの中の形は**デコードしていません**。全部水のブロックは水です。一部水のブロックでは、水のマップ（`height_w.dat`。ハイトマップと同じ符号化）が地面より高いところが水で、湖の隣では、地面が湖より高くないところが水です。陸のブロックは乾いています。これにより、水のマップだけでは水と報告される湿地が取り除かれます。出力の格子より細い川は、断片に壊れて出ます |
| 町の範囲（`textures.tini` が挙げる装飾のメッシュ: `towns.mesh`、`cities.mesh`、`city_*.mesh`、`roads_fields.mesh` など。25.6kmのタイルの、テクスチャ付きの平らな三角形） | すべてのマップで読みます。テクスチャが町、村、工業用地である面を残します。いくつかのマップで、実際の町に対して確認しました（川の両岸にまたがる町、合流点）。これらは範囲です。建物はゲームが実行時に置くもので、ファイルには建物は入っていません |
| 飛行場、橋、建物 | **読みません**。飛行場はミッションのオブジェクトで、建物はゲーム自身の配置から来ます |
| 森（`forest_map.wtr`） | そのブロックは同じように読めますが、ほぼすべてのブロックが「一部森」なので、ビットストリームがなければ使える森のマスクはありません。描いていません |
| 地面のテクスチャ | 読みません |

## ハイトマップの符号化 {#the-heightmap-codec}

データファイルだけから解明しました。ゲームのコードは読んでおらず、逆アセンブルもしていません。リトルエンディアン:

```text
u32 width, u32 height, u32 sectorsX, u32 sectorsY, u32 sectorSize, f32 cellSize
u32 offset[sectorsX * sectorsY]            ファイルの先頭から、行優先、上の行が先
sector: u16 count（続くバイト数）, u16 mode ((log2 sectorSize) << 4 | LW, LW = 4),
        その後、MSBから読むビットストリーム:
  PRE   2 * (log2(sectorSize) - 5) ビット。これまでは常に 0
  LIT   最初のサンプル: 符号 (1)、n (LW ビット)、大きさ (n + 1 ビット)
  セクターが埋まるまで:
    0 LIT       次 = 前 + LIT
    1 RUN LIT   前のサンプルが RUN 回繰り返す（k: 3 ビット、m: k + 1 ビット、RUN = m + 1）。
                その後（セクターが埋まっていなければ） 次 = 前 + LIT
  値は16ビット: 65536 で割った余りとして読みます
```

右端と下端の部分的なセクターは、詰め物をして切り取ります。同じ符号化が、水のマップと遠景用LODのハイトマップにも使われています。

## 目印による位置合わせ {#landmark-fits}

マップの四隅が使えない場合は、`landmarks.py` が、ゲームの距離から地球への、アフィン変換を最小二乗法で当てはめます。ゲームの位置は、あなた自身のファイル（ミッションの `Airfield` ブロック、キャリアの位置データベース）から、実際の位置は、コード内にある場所の公表された座標の表から取ります。JSONの `georeference` には、行列、原点、すべての目印とその残差、そして二乗平均平方根が入っています。
